## 🐞 ۱. مشکل Thread-Local Storage در محیط Green Threads (باگ بحرانی)

**کجا؟**  
- `ol_actor.c`: `static __thread ol_actor_t* g_current_actor` در تابع `ol_actor_self()` استفاده شده.  
- `ol_actor_process.c`: `static __thread ol_process_t* g_current_process` در `ol_process_self()` استفاده شده.  
- `ol_green_threads.c`: هر worker thread یک `g_thread_scheduler` (thread-local) دارد.

**مشکل چیست؟**  
Scheduler از چندین worker thread (مثلاً ۴ تا) استفاده می‌کند و هر worker thread می‌تواند چندین green thread را به صورت هم‌روند روی همان OS thread اجرا کند (زمان‌بندی پیش‌گیرانه یا همکارانه). در این حالت، thread-localها **برای همه‌ی green threadهای یک worker یکسان هستند**. وقتی یک green thread (مثلاً Actor A) در worker thread ۱ اجرا می‌شود، `g_current_actor` را روی A تنظیم می‌کند. سپس scheduler به green thread B در همان worker thread سوئیچ می‌کند، اما `g_current_actor` همچنان به A اشاره می‌کند. در نتیجه `ol_actor_self()` در B مقدار اشتباه برمی‌گرداند.

**راه‌حل:**  
Thread-localها برای شناسایی green thread جاری مناسب نیستند. به جایش:
- یک فیلد `current_actor` به `ol_gt_scheduler_t` اضافه کنید (یا مستقیماً از `ol_gt_t` فعلی استفاده کنید).
- هنگام سوئیچ context در scheduler (مثلاً در `ol_gt_yield` یا `ol_gt_resume`)، این فیلد را به‌روز کنید.
- توابع `ol_actor_self()` و `ol_process_self()` باید از طریق `ol_gt_current()` scheduler جاری را گرفته و سپس `current_actor` را از scheduler بخوانند.

**مثال اصلاح (در `ol_green_threads.h`):**
```c
typedef struct ol_gt_scheduler {
    // ... سایر فیلدها
    ol_actor_t* current_actor;   // actor جاری در این scheduler
} ol_gt_scheduler_t;
```

در `ol_actor_process_entry()` قبل از اجرای behavior:
```c
g_thread_scheduler->current_actor = actor;
```
و در `ol_actor_self()`:
```c
ol_actor_t* ol_actor_self(void) {
    ol_gt_scheduler_t* sched = ol_gt_current_scheduler(); // باید تابعی برای دریافت scheduler جاری اضافه کنید
    return sched ? sched->current_actor : NULL;
}
```

## 🐞 ۲. باگ در `ol_arena_expand_pool` پس از کپی (Memory Corruption بالقوه)

**کجا؟**  
`ol_actor_arena.c`، تابع `ol_arena_expand_pool` در حالت fallback (وقتی که نمی‌توان درجا expand کرد).

**مشکل چیست؟**  
وقتی arena با `mmap` یا `VirtualAlloc` جدیدی allocate می‌شود و داده‌ها از حافظه قدیم به جدید کپی می‌شوند، **اشاره‌گرهای داخل arena (مثل `free_list`، `next` در free blocks) به آدرس‌های مطلق اشاره می‌کنند**. بعد از کپی، این آدرس‌ها هنوز به حافظه قدیم اشاره دارند و باعث دسترسی به حافظه آزاد شده یا داده‌های نامعتبر می‌شوند.

**راه‌حل:**  
- پس از کپی، باید کل free list را بازسازی کرد (مثلاً با پیمایش بلوک‌های آزاد و اصلاح اشاره‌گرها بر اساس offset از ابتدای arena جدید).  
- یا می‌توان به جای ذخیره آدرس مطلق، از **offset** استفاده کرد (مثلاً `uintptr_t offset = (uintptr_t)ptr - (uintptr_t)arena->header`). اما این تغییر بزرگی در طراحی است.

**پیشنهاد سریع:**  
پس از کپی، تابعی مانند `ol_arena_rebuild_free_list(arena)` بنویسید که کل free list را با پیمایش بلوک‌ها (که اکنون در مکان جدید هستند) و تنظیم اشاره‌گرها به آدرس‌های جدید، بازسازی کند.

## 🐞 ۳. نشت حافظه در `ol_actor_destroy` به دلیل عدم پردازش پیام‌های باقی‌مانده

**کجا؟**  
`ol_actor.c`، تابع `ol_actor_destroy`.

**مشکل چیست؟**  
اگر actor در حالی که پیام‌هایی در mailbox دارد (مثلاً در صف ring buffer یا overflow list) destroy شود، این پیام‌ها نشت می‌کنند، چون `actor_mailbox_destroy` هیچ destructor را فراخوانی نمی‌کند (طبق کامنت). در `ol_actor_destroy` ابتدا `ol_actor_close` صدا زده می‌شود که فقط state را CLOSED می‌کند. سپس پس از timeout (اگر actor هنوز در حال اجرا باشد)، `actor_mailbox_destroy` فراخوانی می‌شود بدون اینکه پیام‌ها پاک شوند.

**راه‌حل:**  
قبل از تخریب mailbox، باید تمام پیام‌های موجود را با استفاده از `msg_dtor` پاک کنید. این کار را می‌توانید با یک حلقه روی ring buffer و overflow list انجام دهید.

**کد اصلاحی:**
```c
static void actor_mailbox_clear(actor_mailbox_t* mb, ol_actor_msg_destructor dtor) {
    if (!mb) return;
    // پاک کردن ring buffer
    size_t i = mb->head;
    while (i != mb->tail) {
        if (mb->ring_buffer[i] && dtor) dtor(mb->ring_buffer[i]);
        i = (i + 1) % mb->capacity;
    }
    // پاک کردن overflow list
    for (size_t j = 0; j < mb->overflow_count; j++) {
        if (mb->overflow_list[j] && dtor) dtor(mb->overflow_list[j]);
    }
    mb->overflow_count = 0;
}
```
و در `ol_actor_destroy` قبل از `actor_mailbox_destroy` این تابع را صدا بزنید.

## 🐞 ۴. شرط مسابقه (Race Condition) در مقداردهی اولیه `ol_get_page_size`

**کجا؟**  
`ol_actor_arena.c`، تابع `ol_get_page_size` (static inline).

**مشکل چیست؟**  
یک متغیر static `page_size` بدون هیچگونه هماهنگی (mutex یا atomic) مقداردهی اولیه می‌شود. اگر چند thread به طور همزمان اولین بار این تابع را صدا بزنند، ممکن است مقداردهی چندباره (یا مقدار نامعتبر) رخ دهد.

**راه‌حل:**  
استفاده از `call_once` (C11) یا یک mutex ساده. مثلاً:
```c
static size_t ol_get_page_size(void) {
    static size_t page_size = 0;
    static ol_mutex_t init_mutex = OL_MUTEX_INITIALIZER; // فرض کنید OL_MUTEX_INITIALIZER تعریف شده
    if (page_size == 0) {
        ol_mutex_lock(&init_mutex);
        if (page_size == 0) {
#if defined(_WIN32)
            SYSTEM_INFO si; GetSystemInfo(&si); page_size = si.dwPageSize;
#else
            page_size = sysconf(_SC_PAGESIZE);
#endif
        }
        ol_mutex_unlock(&init_mutex);
    }
    return page_size;
}
```

## 🐞 ۵. باگ در `ol_actor_send_timeout` (مقدار بازگشتی اشتباه)

**کجا؟**  
`ol_actor.c`، تابع `ol_actor_send_timeout`.

**مشکل چیست؟**  
طبق مستندات، `ol_actor_try_send` مقادیر ۱ (موفق)، ۰ (full) و ۱- (خطا) برمی‌گرداند. در `ol_actor_send_timeout` اگر `ol_actor_try_send` موفق شود (`result == 1`)، تابع `return result;` می‌کند که ۱ است. اما قرارداد این تابع احتمالاً برگرداندن ۰ برای موفقیت است (چون timeout اتفاق نیفتاده). در نتیجه caller ممکن است اشتباهاً فکر کند timeout شده است.

**راه‌حل:**  
پس از موفقیت، `return 0;` کنید.

## 🐞 ۷. ریسک بن‌بست (Deadlock) در `ol_parallel_flush` هنگام shutdown

**کجا؟**  
`ol_parallel.c`، تابع `ol_parallel_shutdown` و `ol_parallel_flush`.

**مشکل چیست؟**  
اگر `ol_parallel_shutdown` با `drain = true` صدا زده شود، `ol_parallel_flush` فراخوانی می‌شود. در `ol_parallel_flush`، workerها در حال اجرای تسک‌ها هستند و ممکن است تسک‌ها سعی کنند تسک جدیدی به همان pool اضافه کنند. این می‌تواند باعث deadlock شود، زیرا `ol_parallel_submit` در هنگام shutdown (`running = false`) خطا می‌دهد و ممکن است تسک‌ها منتظر بمانند.

**راه‌حل:**  
- در مستندات ذکر کنید که در هنگام shutdown، نباید تسک جدیدی به pool اضافه شود.  
- یا می‌توان در `ol_parallel_submit` اگر `shutting_down` true است، اما تسک از طرف یکی از workerهای خود pool است، اجازه اضافه شدن بدهید (با بررسی thread ID). این پیچیده‌تر است.

## 🐞 ۸. احتمال data race در `ol_reactive.c` به دلیل عدم محافظت از callbackهای کاربر

در `ol_subject_on_next`، پس از خروج از mutex، callback کاربر (`on_next`) صدا زده می‌شود. اگر کاربر در callback دوباره روی همان observable عملی انجام دهد (مثل unsubscribe)، ممکن است data race رخ دهد. این مشکل در بسیاری از کتابخانه‌های reactive دیده می‌شود و معمولاً با deferring یا استفاده از scheduler حل می‌شود. می‌توانید از event loop برای اجرای callbackها استفاده کنید.

## 🐞 ۹. مصرف CPU در حلقه‌های انتظار با `usleep`

**کجا؟**  
`ol_actor_destroy` و `ol_supervisor_stop` و موارد مشابه که از `usleep` در حلقه‌های busy-wait استفاده شده.

**راه‌حل:**  
- به جای `usleep`، از `ol_cond_wait_until` با timeout استفاده کنید تا thread واقعاً blocked شود و CPU مصرف نکند.  
- یا از eventfd / pipe برای بیدار شدن استفاده کنید.

## 🐞 ۱۰. مشکل سازگاری با ویندوز (MSVC) در استفاده از __atomic

**کجا؟**  
در `ol_green_threads.c` و `ol_actor.c` از `__atomic` builtins استفاده شده که مختص GCC/Clang است. در ویندوز با MSVC اینها کار نمی‌کنند.

**راه‌حل:**  
یک لایه انتزاعی برای عملیات اتمی بنویسید (مثلاً `ol_atomic_store`، `ol_atomic_load`، `ol_atomic_cas`) که بسته به کامپایلر از `__atomic`، `_Interlocked`، یا `stdatomic.h` استفاده کند.

## 🛠️ پیشنهادات برای بهبود و پیشرفت پروژه

1. **افزودن ابزارهای تست و پروفایلینگ**:
   - از **ThreadSanitizer** (سانیتایزر thread) برای شناسایی race conditions استفاده کنید. اجرای برنامه تحت TSan بسیاری از مشکلات را نشان می‌دهد.
   - از **AddressSanitizer** و **Valgrind** برای یافتن memory leaks و use-after-free استفاده کنید.
   - یک سری تست‌های stress با تعداد زیاد actor و پیام‌های هم‌روند بنویسید.

2. **مستندسازی API و افزودن مثال‌های بیشتر**:
   - پروژه شما مستعد تبدیل شدن به یک استاندارد است. مستندات کامل و مثال‌های عملی (مانند ساخت یک سرور HTTP ساده با actorها) جذب جامعه را سرعت می‌بخشد.

3. **ابزارهای مانیتورینگ و دیباگ**:
   - اضافه کردن قابلیت dump state scheduler (مشابه `ol_gt_dump_scheduler_state` که در debug وجود دارد) به صورت رسمی.
   - متریک‌های performance مانند تعداد context switch، کارایی cache و ... .

4. **ساخت binding برای زبان‌های دیگر**:
   - هدف اصلی OLSRT استفاده در زبان‌های مختلف است. با تکمیل C API، می‌توانید bindings برای Python، PHP، Ruby، Node.js و ... ایجاد کنید. این کار قدرت پروژه را چندین برابر می‌کند.

5. **بهبود مقیاس‌پذیری allocator**:
   - در حال حاضر هر arena یک mutex دارد که ممکن است گلوگاه شود. می‌توانید از thread-local caches یا lock-free allocator (مانند mimalloc) استفاده کنید.

6. **حذف thread-local برای current actor/process** (که قبلاً اشاره شد).

7. **استفاده از model checking**:
   - ابزارهایی مانند **TSan** و **Loom** (برای Rust) اما در C می‌توانید از **CDSChecker** یا **Relacy** برای مدل‌سازی concurrent algorithms استفاده کنید.

8. **پشتیبانی از distributed actors** (مانند Erlang nodes):
   - ارتباط بین پردازه‌ها در ماشین‌های مختلف از طریق شبکه می‌تواند OLSRT را به یک پلتفرم توزیع‌شده واقعی تبدیل کند.
