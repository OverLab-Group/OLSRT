# v1.3.4 — Real cooperative scheduler (x86_64 asm)

## What this patch does

Replaces the v1.3.2/v1.3.3 workaround (which bypassed the context
switch entirely and called `gt->entry(gt->arg)` directly) with a
**real cooperative scheduler** using the existing x86_64 asm context
code, now fixed to satisfy the SysV ABI.

### The three bugs fixed

1. **Wrong stack setup in `ol_ctx_make_x86_64`.** The v1.3.2 code
   stored the argument in `%rbx` (ignored by SysV) and set up a
   return-address slot that no function ever returned to. The
   trampoline saw `arg = garbage`.

2. **`ol_gt_run_to_completion` bypassed the scheduler.** It called
   `gt->entry(gt->arg)` directly, so `yield` never swapped anywhere
   real. Every "green thread" was a plain function call.

3. **`g_gt_driver_ctx` was never written.** `ol_gt_yield` referenced
   it but nothing saved the driver's context, so the "return to
   driver" path was dead code.

### How it works now

```

driver (ol_gt_run_to_completion)          green thread (ol_gt_trampoline)

---

ol_ctx_save(driver_ctx)   ────┐
│
while state != DONE:          │
ol_ctx_restore(gt) ───────┼────────► asm trampoline
│              │
│              ▼
│          ol_gt_trampoline(gt)
│              │
│              ▼
│          gt->entry(gt->arg)
│              │
│              ▼
│          ol_gt_yield()
│              │
│              ▼
│          ol_yield_impl ─────┐
│              │              │
│              │              ▼
└──── resume ┴──────► driver_ctx
│
▼
(loop repeats)

```

## What to expect on the benchmark

Before v1.3.4: `olsrt/08_coroutines` was 114 ms
(`wall_time_ms: 114.472`). That was init cost + 1000 sequential
direct-calls. No scheduler.

After v1.3.4: **expect 5–30 ms**. The scheduler now actually runs.
The number is smaller because:

- Real yields are cheap asm `jmp`, not function calls that stack up.
- 1000 ping-pongs run in the driver loop with minimal overhead.

If it's still ~114 ms, the patch didn't take — check `marker count`.

## Limitations

- **x86_64 POSIX only.** aarch64, ARM, Windows keep v1.3.3 behaviour.
No cross-platform regression.
- **No nested drivers.** `g_gt_driver_ctx` is a single global per
thread. Running `ol_gt_run_to_completion` from inside a green
thread would clobber the outer driver. Not exercised by current
code (`ol_process_driver_thread` starts a fresh thread per actor).
- **No legacy-path fix.** Non-driver `ol_gt_yield` remains a no-op
(v1.3.3 behaviour). This affects coroutines, which have their own
scheduling issue — a separate v1.3.5 task.
