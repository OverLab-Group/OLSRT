Show HN: OLSRT – a C11 concurrency runtime, and what its benchmark against libuv actually shows

I wrote OLSRT, a C11 concurrency substrate: actors, channels, promises, an event loop with timers and TCP, supervisor trees, dataflow graphs, reactive streams, and a green-thread API, in one library with a stable C ABI. Apache 2.0.

Two weeks ago I shipped v1.3.2 with "production-ready" in the README. Then I found 46 bugs, of which 8 were crash-level. This post is about what I did next: fix all 46, write a regression suite that would have caught every one of them, add a benchmark against libuv, and write down every number, including the ones where OLSRT loses.

Three lessons that came out of it:

1. Green CI means the tests you wrote pass, not that the code works. The old regression suite used ol_actor_reply_ok exclusively, so the double-free in ol_actor_reply_error never fired. It built demos/08_coroutines but never ran it. 28 assertions across 12 subsystems.

2. A demo that is built but not executed is not a test. Running the benchmark for the first time found a hang in demo 08 that had been in the repo since v1.3.2. That was bug #47.

3. Honest benchmarks need fair labels. Four of sixteen demos compare a primitive both runtimes ship (native). The other twelve compare an OLSRT primitive against the closest pthread equivalent, because libuv does not ship the primitive (built). Treating them as the same number is dishonest to both sides.

The numbers, plainly. Machine: AMD E2-1800, 2 cores, Debian 13, libuv 1.50. Deliberately modest — the ratios travel, the absolute numbers don't.

Native comparisons (both runtimes have the primitive):

  03 parallel pool (100 tasks, 4 workers): parity. hyperfine
     10 runs gave OLSRT 10.1ms +/- 3.1, libuv 11.9ms +/- 3.3,
     ratio 1.18 +/- 0.49 — confidence interval includes 1.0.

  04 timers (one-shot + periodic, 400ms window): parity,
     400.5ms vs 400.2ms.

  07 HTTP (100 requests, 10 concurrent, via ab): libuv
     3.4x faster, 2776 req/s vs 818 req/s.

  12 semaphores (8 threads, cap 2): parity, 405.6ms vs 402.5ms.

Emulated comparisons (libuv mirror is pthread, because libuv has no primitive):

  01 hello_actor (1000 ask/reply round-trips): OLSRT 2.1x
     faster, 48ms vs 104ms. Real win: actor + ask/reply beats
     uv_queue_work per request.

  02 channel (1M messages): contested. Runs varied between
     OLSRT 21% faster and libuv 20% faster. On two cores this
     is scheduler noise.

  05 promise (1000 ops): libuv 6.4x faster, 0.32ms vs 2.05ms.
     Cost of OLSRT's refcount and continuation tracking.

  06 dataflow (1000 items): libuv 1.4x faster.

  08 coroutines (1000 yields): libuv 1.5x faster.

  09 supervisor (3 children, 1 crashes): libuv 7.9x faster.
     Not overhead — OLSRT's crash scan is a 100ms poll, libuv
     fires exit_cb immediately. The ratio is the poll interval.

  10/11 reactive + streams: libuv 1.75-1.85x faster.

  13 actor_supervisor: libuv 180x faster. Same 100ms poll
     interval, plus the per-actor cost of the supervisor slot.

  14 actor_channel: libuv 1.85x faster.

  15 reactive_loop (10 ticks @ 50ms): parity, 500ms,
     timer-bound.

  16 full_stack: not measured. Network race in the demo's
     internal client. Will fix before the next release.

What the numbers mean:

  OLSRT is not faster than libuv in general. On the four native
  rows: one contested tie, two parities, one loss (07, 3.4x).
  That is a peer on the primitive subset, not a leader.

  The 5-6x losses on promise and channel are the cost of the
  abstraction existing. A hand-rolled pthread mutex + condvar
  that only does wait/signal is lighter than a refcounted
  promise with continuations. Design trade, not a bug.

  The 7.9x and 180x numbers on supervisors measure the 100ms
  poll interval, not runtime overhead. v1.3.5 moves to
  event-driven supervision and the ratio drops to 2-3x.

Status, plainly:

  Green threads: API only. The x86_64 context switch has an
  argument-passing bug (%rbx vs %rdi); the driver bypasses it
  and calls the entry function directly. Real cooperative
  scheduling lands in v1.3.4. Consequence: actor limit is the
  OS thread limit (~10k on Linux), not the 100k+ a real
  scheduler enables.

  Process isolation: thread + per-actor arena, not fork. A
  wild pointer in one actor can still corrupt another.
  fork-based isolation is v2.0.

  Dataflow fan-out: unsafe. Two edges from one port will
  double-free the item. Attach at most one edge per port until
  v1.3.4.

  Fuzzing: none. The gold_ws HTTP parser in particular would
  benefit from libFuzzer.

  Cross-platform: Linux x86_64 + BSD. Windows and macOS are
  v2.0.

What v1.3.3 fixed: 46 bugs — 8 P0 (double-free in reply_error,
non-atomic child ID in supervisor, multi-hop dataflow silently
stalled at one hop, three TSan-visible races in actor/process/
supervisor state), 21 P1 (condvar handshake, supervisor restart
race, subject shallow-copying a pthread_mutex_t), 17 P2
(atomic-mixing, stack pool sizing, missing Doxygen). New
regression suite has 30 assertions across 6 tests; each one
triggers a specific bug from the list. CI is 23/23 green with
all four sanitizers clean. First time in the project's history
that was true.

If you evaluate for production: don't. Not yet. The primitives
work, but the green-thread scheduler is a stub, "isolation" is
a promise the code does not keep, and fuzzing is absent. v1.3.4
(scheduler) and v2.0 (fork isolation) are the milestones that
change that.

If you want to write C concurrency code, contributions are
welcome. Highest-value tasks:

  - Fuzzing gold_ws's hand-written HTTP parser
  - A real green-thread context switch (fix %rbx vs %rdi, or
    rewrite on ucontext)
  - Windows IOCP and macOS kqueue pollers
  - Event-driven supervisor to replace the 100ms poll

Apache 2.0. Feedback welcome, especially on the benchmark
numbers — the whole file is reproducible with one command.

  make -C demos && make -C demos/bench && bash demos/bench/bench-run.sh
