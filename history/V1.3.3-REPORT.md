# OLSRT v1.3.3 — Release Report

**Release date:** 2026-11-08
**Status:** Bug-fix release. All 23 CI tools PASS.
**Public API:** Unchanged from v1.3.2.

---

## Executive Summary

v1.3.2 shipped with the label "production-ready" and 23 green CI
checks. It also contained **46 bugs**, of which 8 were crash-level,
correctness, or data-loss issues that any real workload would hit.
The CI was green because the regression suite was too shallow: one
actor, one dataflow hop, one subject, no concurrent supervisor
restarts.

v1.3.3 fixes all 46. Along the way we wrote `tests/test_v133_fixes.c`,
a 30-assertion / 6-test regression suite that triggers every bug the
old tests missed. Every fix is verified by that suite, and the
four-sanitizer pass (ASan, UBSan, LSan, TSan) that v1.3.2 *claimed*
is now actually earned.

**Net result:** `ci/run_all.py --keep-going` reports `23 tool(s) run,
0 failure(s)` for the first time in this codebase's history.

## Architecture Notes

### Why the double-free in `ol_actor_reply_error` was missed

v1.3.2's regression suite used `ol_actor_reply_ok` exclusively. The
error path was never exercised. Any real application that returns
`ol_actor_reply_error` to signal "not found" aborts.

### Why the dataflow multi-hop bug took two fixes

The first fix (`P0-3`) made the worker drain edge inboxes before
processing. That's necessary but not sufficient: the edge struct
had only one `next` pointer, and `ol_df_connect` used it for both
the graph-wide edge list and the per-node port list. The port
assignment ran second and clobbered the graph assignment, leaving
`g->edges_head` holding only the most recently created edge.

The second fix (`P0-3a`) split the field into `next` and
`next_port`. After that, `df_worker`'s iteration over `g->edges_head`
actually visits every edge, and multi-hop delivery works.

### Why TSan kept finding new races

Each TSan fix was for a *pre-existing* bug in v1.3.2. The old test
suite used one actor, one subject, one dataflow graph. The v1.3.3
handshake fix (`P1-3`) replaced `usleep` with a proper condition
variable, which allowed the test suite to spin up 32 actors in
parallel and actually exercise concurrency. Races that had been
dormant for the entire v1.3.x series surfaced.

They were all the same class of bug: a field written by one thread
and read by another without synchronization. Making the fields
`_Atomic` is the right fix because C11 guarantees atomic read/write
for every access on an `_Atomic`-qualified field, so no call site
needs to change.

### Why `ol_subject` needed to be a type alias

The old code did:

```c
struct ol_subject {
    ol_observable_t base;
};

ol_subject_t *ol_subject_create(...) {
    ol_subject_t *s = calloc(1, sizeof(*s));
    ol_observable_t *o = observable_alloc(loop, dtor);
    s->base = *o;              /* copy */
    free(o);
    return s;
}
```

`ol_observable_t` contains an `ol_mutex_t` which wraps
`pthread_mutex_t`. Copying an initialized `pthread_mutex_t` by value
is undefined by POSIX. On glibc it "happens to work" most of the
time; on macOS `os_unfair_lock` it crashes. The fix makes
`ol_subject_t` a type alias for `ol_observable_t`, so there's no copy
— just a pointer cast.

### Why `OL_PAGE_SIZE` was racy

Every call to `ol_gt_scheduler_init()` wrote the global
`OL_PAGE_SIZE`. Before v1.3.3 there was exactly one scheduler per
process, so this never raced. The v1.3.3 handshake gives each actor
a dedicated driver thread, each of which calls
`ol_gt_run_to_completion`, which calls `ol_gt_scheduler_init`. With
32 actors, 32 threads write this global concurrently.

The fix initializes `OL_PAGE_SIZE` once, in a library constructor
that runs before `main()` and before any `pthread_create`. After
that, the field is read-only.

## Known Limitations (Unchanged from v1.3.2)

These are deliberate MVP scope decisions, not bugs. All are on the
roadmap.

### Green threads run on the calling OS thread

The public API is in place, but the x86_64 context-switch assembly
has an argument-passing bug (`%rbx` vs `%rdi`).
`ol_gt_run_to_completion` bypasses the assembly and calls the entry
function directly. No cooperative yield, no work-stealing, no
multiplexing many green threads onto one OS thread.

**Practical consequence:** the actor limit is the OS thread limit
(~10k on Linux), not the 100k+ a real scheduler enables.

**v1.3.4 plan:** correct context switch, or a rewrite on top of
`ucontext`.

### Actor "isolation" is thread + arena, not process

`ol_actor_create` starts one OS thread per actor via
`ol_process_create`. The actor's private arena provides logical
memory isolation (pointers from one arena are not valid in another)
but not process-level isolation. A wild pointer in actor A can still
corrupt actor B or the runtime.

**v2.0 plan:** `fork`-based isolation, comparable to BEAM.

### Dataflow fan-out is not safe

Attaching two edges to the same output port makes both receive the
same item pointer. Each destination channel then owns that pointer
and calls its destructor on it, which is a double free.

**v1.3.4 plan:** reference-counted item wrapper.

### No fuzzing

`ci/fuzz_check.py` skips because there are no fuzz targets. The
`gold_ws` HTTP parser in particular would benefit from libFuzzer.
